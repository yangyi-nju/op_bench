# OpBench v0.7 P4 Dataset Freeze and Validation Cohort Design

日期：2026-07-27

状态：Approved for implementation。用户已授权在不逐项确认的前提下完成整个
v0.7，并由实现者选择最优工程方案。

## 1. 目标

P4 把 P2 恢复的 2 条 Precision Task、P3 新增的 6 条 Boundary Task 和 v0.5
继承的 17 条 Task 冻结为三个可重建、可验证的数据清单：

- `pytorch_v0.7`：25 条累计 Task；
- `pytorch_v0.7_boundary`：6 条 Boundary Task；
- `pytorch_v0.7_precision`：8 条 Precision Task。

随后使用 v0.6 Runtime/Evaluation/Integrity 协议和真实
`codex_mcp_canonical` Adapter，对 6 条新 Boundary Task 运行 3-repeat
Validation Cohort，共 18 个有效 Attempt。Validation 只验证新任务的可运行性、
难度信号和失败归因，不形成正式跨 Agent 排名。

## 2. 前置证据修正

P4 预检发现 `pytorch__147352__storage_offset_overflow` 复用了
`pytorch-boundary-cpu-source-build-py311` 环境，但 Task 的
`runtime_tier` 被误写为 `cuda_kernel_build`，且 test timeout 为 300 秒。环境
Registry 的真实层级是 `cpu_source_snapshot_fuller`，同一 Base Commit 的完整
CPU source build Admission 实际需要约 11–14 分钟。

这不是 Dataset Composer 可以忽略或映射掉的差异。修正流程必须：

1. 先增加 Dataset/Boundary artifact 测试，要求 Task tier 与 Environment Registry
   一致；
2. 把 Task tier 改为 `cpu_source_snapshot_fuller`，test timeout 改为 900 秒；
3. 重新运行 Compatibility、preflight、Baseline/Gold Admission；
4. 使用新的 replay hash 重新生成 8 阶段 Factory Admission；
5. 更新 P3 报告中的证据身份和时长。

不得直接修改旧 Admission/Factory JSON，也不得把 CPU source-build 环境伪装为
CUDA kernel profile。

## 3. 方案选择

评估了三种冻结方案：

1. **Boundary Factory Freeze + Release Composition（采用）**：P3 的 6 条新任务
   使用 P1 的完整 Factory Freeze；累计集和 Precision 集通过内容寻址的 Release
   Composition 继承已验证清单并加入 P2/P3 任务。优点是保留真实 provenance，
   不改变 P1 合同，且三个输出都可重建。
2. **扩展 Dataset Freeze v1 的 base 继承语义**：让 Freeze 自动合并
   `base_dataset`。这会改变已经冻结的 v1 语义，使旧 synthetic freeze 和 P1
   验收需要重新解释，版本收益不足。
3. **给 19 条继承/恢复任务补造 Factory 链**：形式统一，但历史任务没有 P1
   Candidate/Decision provenance，事后生成会把“Release 继承”错误表述成“Factory
   新发现”，属于不可接受的证据伪造。

采用方案 1。Factory Freeze 继续只表示“本轮由 Factory 选择的任务”；Release
Composition 只表示“从哪些已验证输入组成哪个发布切片”。两个合同职责分离。

## 4. Boundary Factory Freeze

`factory/v0.7/p4/boundary_freeze_request.json` 明确绑定：

- v0.5 base Dataset；
- Factory Protocol、Screening Rule Set 和 Exclusion Index；
- Environment/Source Registry；
- 6 条 Candidate、Decision、Task、Admission Evidence、Environment、Source 和
  final verified Factory Admission 引用；
- 每个引用的 canonical content hash；
- 固定 UTC `created_at`。

官方 `freeze_dataset.py` 生成：

```text
factory/v0.7/p4/boundary_freeze/
  freeze_manifest.json
  dataset.json
```

`dataset.json` 必须能由 `freeze_manifest.json` 逐字节重建。任何 Admission 不是
verified、引用 hash 漂移、Task ID 重复或 evidence 缺失都 fail closed。

## 5. Release Composition 合同

新增 `DatasetReleaseManifest` v1，职责是确定性组合已验证 Dataset，而不是重新
声明 Factory provenance。

输入：

- `cumulative_base`：`datasets/pytorch_v0.5/dataset.json`；
- `precision_base`：`datasets/pytorch_v0.5_precision/dataset.json`；
- `boundary_freeze`：P4 Boundary Freeze 生成的 Dataset；
- `restored_precision`：#129154、#144073 的 Task 和 Admission Evidence 引用；
- Environment/Source Registry 引用；
- 固定输出 ID、version 和 UTC `created_at`。

每个输入保存 normalized repo-relative path 和 `sha256:` canonical file hash。
Composer 在构建前执行正式 Dataset validation，并对每条 Task 重新加载
`task.json` 和 Admission Evidence，确认：

- Task、Evidence 和 Dataset entry 的 Task ID 一致；
- Task admission 为 verified；
- replay hash 与当前 bundle 一致；
- Task runtime tier 与 Environment Registry 一致；
- Source Base Commit 与 Source Registry 一致；
- entry path 规范化且任务在切片内只出现一次。

输出任务条目统一为：

```json
{
  "task_id": "...",
  "task_path": "tasks/...",
  "admission_status": "verified",
  "admission_evidence": "tasks/.../admission/evidence.json",
  "environment_status": "ready",
  "runtime_tier": "...",
  "source_status": "ready",
  "replay_status": "verified"
}
```

排序使用以下规则：

- inherited Task 保持输入 Dataset 的顺序；
- restored Precision 按 Task ID 排序后追加；
- Boundary 按 Factory Freeze 的 Task ID 顺序追加；
- Slice 内重复 Task ID 是合同错误，不静默去重。

输出集合必须精确满足：

```text
cumulative = cumulative_base ∪ restored_precision ∪ boundary_freeze
precision  = precision_base ∪ restored_precision
boundary   = boundary_freeze
```

Release Manifest 保存三个生成 Dataset 的 canonical hash、Task 数量和输入引用，
并以这些字段派生 `release_id`。`rebuild_release_datasets()` 必须从 Manifest
内冻结的 normalized entries 重建三个输出并重新校验 hash。

## 6. Slice Summary

每个 Dataset 同目录生成 `summary.json`。Summary 从实际 Task Manifest 而非仅从
Dataset entry 聚合：

- task count 和 admission/source/environment/replay 状态；
- runtime tier；
- problem dimension；
- problem subclass；
- failure contract；
- verified Admission evidence 数。

Summary 保存 Dataset canonical hash。重建时先验证 Dataset，再生成 Summary；
因此累计、Boundary、Precision 的统计不能手工编辑。

## 7. v1 Agent Source Loading

当前 v1 evaluator 会在 fresh lease 中执行 Python overlay 或 inplace build，但
Agent 的 `test_run` 直接执行 selector：

- Python overlay 测试可能导入容器内原始 wheel，而不是 Agent 刚编辑的文件；
- inplace-build 测试可能在扩展未编译时导入完整源码。

P4 增加一个共享、确定性的 Runtime Source Loading command builder，并让
`RegisteredTest` 可携带可选 preparation command。`test_run` 顺序为：

```text
sync authoritative workspace
  → source preparation
  → registered public selector
```

约束：

- `none` 不执行 preparation；
- `python_overlay` 把声明的 overlay paths 同步到固定 runtime site-packages，
  Runtime Backend 为普通 Python command 注入该路径；
- `inplace_build` 使用与 fresh evaluator 相同的 `build_ext --inplace` 命令和
  build environment；
- preparation 使用剩余 action deadline 和 Runtime Profile timeout 的较小值；
- preparation 失败时 selector 不执行，Action Observation 保留 exit code、
  bounded stdout/stderr、duration 和 timeout；
- preparation 不改 Agent patch scope，也不把 Hidden Test 暴露给 Agent；
- evaluator 仍在独立 fresh lease 中重新加载源码，Agent 阶段成功不能替代评分。

任意 command action 不自动触发 build，只有正式 `test_run` 触发，保持旧
WorkspaceActions 语义并避免每次读写后无意义重编译。

## 8. Runtime Profiles

新增五个 digest-pinned v1 Runtime Profile：

| Profile | Task | Source loading |
| --- | --- | --- |
| `remote-cpu-boundary-torch2.2-py311-v1` | #117065 | Python overlay |
| `remote-cpu-boundary-torch2.3-py311-v1` | #118762 | Python overlay |
| `remote-cpu-boundary-torch2.4-py311-v1` | #126461 | Python overlay |
| `remote-cpu-source-boundary-py311-v1` | #143792, #147352 | inplace build |
| `remote-cuda-boundary-torch2.6-cu124-v1` | #139751 | Python overlay |

Profile 的 image digest、platform、GPU 要求、source loading mode 和 hardware
identity 必须来自 Registry；`legacy.py` 仅增加 Environment ID 到 Profile ID 的
显式映射。一个 Environment ID 不能映射到多个不同 timeout/tier，因此两个
source-build Task 统一为 900 秒。

## 9. Validation Cohort 合同

现有 MCP report builder 把 v0.6 的四个 cohort 写死。P4 将合同推广为“一个或
多个、Task 分区互斥的 cohort”，同时保持
`FORMAL_MCP_EXPERIMENT_CONTRACT` 的 4 cohort / 51 Attempt 字节与行为兼容。

新增合同 JSON 的严格 `to_dict/from_dict`：

```json
{
  "dataset_identifier": "pytorch_v0.7_boundary",
  "dataset_digest": "sha256:...",
  "platform_version": "opbench-v0.6.0",
  "cohorts": [
    {
      "profile_id": "...",
      "task_repeats": [
        {"task_id": "...", "repeats": [1, 2, 3]}
      ]
    }
  ]
}
```

P4 使用 5 个 cohort、18 个有效 Attempt。报告 builder 要求：

- run root 数量与合同 cohort 数量相等；
- Dataset、platform、profile、Task partition 和 repeat matrix 精确一致；
- 每个 Attempt 恰有一个 valid selected retry；
- fresh Integrity 全通过且与 persisted Integrity 一致；
- Adapter、model、Codex CLI 和 MCP trace identity 一致；
- Action request/observation 完整配对；
- infrastructure-invalid 历史 retry 保留 provider/MCP/runtime 归因；
- 任何缺失、重复或被拼接的结果都拒绝生成公开报告。

`summarize_mcp_experiment.py --contract PATH` 消费显式合同；不传参数时继续使用
v0.6 formal contract。Markdown 标题使用合同 platform/dataset，不再硬编码
“v0.6 MCP Agent Experiment”。

## 10. 真实运行与失败处理

运行顺序：

1. 每个 Runtime Profile 先执行 1 个真实 Codex canary；
2. canary 通过 Runtime、MCP、Integrity 后，使用正式 3-repeat cohort root；
3. transient provider/SSH/container/MCP 失败只在同一 root 中按
   `retry_infrastructure` resume；
4. 只有 valid Attempt 进入 18-attempt Summary；
5. 全部 root 完成后 fresh rebuild Integrity 和公开 report。

结果解释：

- `0/3 resolved` 标记 floor candidate；
- `3/3 resolved` 标记 ceiling candidate；
- `1/3` 或 `2/3` 为中间难度信号；
- Agent 逻辑失败不撤销已通过 Admission 的 Task；
- selector 未执行、source loading 失败、环境 API 漂移或 evaluator setup failure
  属于 Task/Runtime/Infrastructure 问题，必须修复并重跑，不能计作 Agent 失败；
- 不因 Validation 结果调整 Hidden Test 或 Gold Patch；
- 不把本轮单模型 Validation 表述为 leaderboard、模型优劣或反馈因果结论。

## 11. 公开与私有 Artifact

```text

```

```text

  experiment_index.json

```

公开报告只含 Task/Attempt identity、有限指标、hash 和稳定归因；不复制完整 Agent
自由文本、私有运行路径、host、credential 或未裁剪 stdout/stderr。

## 12. 测试与验收

平台改动使用 TDD，至少覆盖：

- #147352 tier/Registry mismatch 的 RED 和重新生成证据后的 GREEN；
- Release Composition 的 exact membership、顺序、hash 和 rebuild；
- input hash drift、重复 Task、非 verified entry、replay drift、Registry drift fail
  closed；
- 三个 Slice Summary 的 taxonomy/runtime/failure-contract 聚合；
- Agent `test_run` 在 selector 前执行 overlay/inplace preparation；
- preparation 失败/timeout 时 selector 不执行；
- arbitrary command 不触发 preparation；
- v0.6 formal MCP report 保持 4 cohort/51 Attempt；
- P4 自定义 5 cohort/18 Attempt 合同 round trip 和完整性门；
- CLI 对恶意路径、symlink、已存在非匹配输出和非 canonical JSON 的拒绝。

P4 完成时必须通过：

1. 三个 Dataset `--require-verified` validation；
2. Boundary Freeze 和 Release Manifest rebuild 逐字节一致；
3. 三个 Summary 可从 Dataset/Task 重建；
4. 6 条 Boundary Task fresh replay hash 与 Admission 一致；
5. 18 个真实 Codex valid Attempt 和 18 条完整 MCP trace；
6. 5 个 cohort fresh/persisted Integrity 全通过；
7. focused tests、全仓 unittest、compileall、全部 tracked JSON、Schema、v0.5
   Dataset compatibility 和 `git diff --check`。

P4 交付后进入 P5 发布文档，不在 P4 提前宣称 v0.7 Completed。
