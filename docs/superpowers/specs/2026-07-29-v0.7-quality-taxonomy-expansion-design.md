# OpBench v0.7 Quality-First 50-Task Release Design

Date: 2026-07-29

Status: Conversational design approved; written-spec review pending

Target release: `opbench-v0.7.0`

## 1. Decision Summary

OpBench v0.7 is reopened before external publication. The final v0.7 release
will no longer be the current 25-Task Boundary-focused snapshot. It will be a
quality-first 50-Task release with:

- all current 25 Tasks reviewed for re-admission under new Prompt and
  complexity gates;
- enough new or replacement Tasks to reach exactly 50 verified Tasks;
- CPU and NVIDIA CUDA coverage;
- a lightweight multi-axis taxonomy;
- Precision, Boundary, and Device retained as derived, overlapping slices;
- answer-leakage checks for the exact Agent-visible Prompt;
- no Task classified as `easy`;
- one Agent regression attempt for each retained historical Task;
- three independent Agent validation attempts for each new or replacement Task.

The following work remains outside v0.7:

- Evaluation/Scoring Specification RC redesign;
- leaderboard or cross-Agent ranking claims;
- MPS, XPU, or other accelerator hardware;
- heavy multi-node distributed workloads;
- Agent reasoning-trace collection or reasoning-based scoring;
- feedback ablation and formal causal comparisons.

## 2. Why v0.7 Is Being Reopened

The existing v0.7 implementation correctly isolates Gold Patch, Hidden Test,
Admission, and private evaluation assets through `FullTaskSpec` and
`AgentTaskView`. The formal v0.7 validation used the
`codex_mcp_canonical` Adapter, so the private/public architecture itself is not
being replaced.

The validity problem is inside the content currently declared public:

- some `statement.body` values describe the internal root cause or the required
  implementation;
- some prompts name the exact helper, branch, expression, or implementation
  path needed by the Gold Patch;
- `CapabilityPolicy.writable_paths` contains Task-specific source paths;
- some `operator_name` values identify internal implementation symbols rather
  than user-facing APIs;
- public Task identifiers contain upstream PR numbers and descriptive slugs;
- several Tasks require little localization, diagnosis, or repair-choice
  reasoning once those hints are visible.

The initial audit of the current 25 Tasks found:

- 24 of 25 `issue.md` files contained direct Fix/PR/path-style hints under the
  conservative audit pattern;
- 23 of 25 Tasks had a one-file Patch Scope;
- 7 Tasks were labeled `easy`;
- 7 Gold Patches changed at most four source lines.

These numbers are risk indicators, not automatic rejection counts. A short
Patch or one-file fix can still require meaningful cross-layer diagnosis. The
correct order is:

1. sanitize the public Prompt;
2. check the sanitized Prompt against private answer-side assets;
3. reassess the Task's reasoning burden;
4. remove the Task only if it remains mechanically simple or otherwise fails
   Admission.

## 3. Release Identity and Pre-Quality Audit Snapshot

The current 25-Task state and its existing validation results become the
`v0.7-pre-quality` audit snapshot.

The audit snapshot records:

- baseline Git commit `4f5addc`;
- the existing cumulative, Boundary, and Precision Dataset hashes;
- the existing validation cohort identities and outcome summary;
- the fact that the snapshot predates Prompt sanitization, historical
  re-admission, and the lightweight taxonomy.

An archive descriptor under `archives/v0.7-pre-quality.json` will bind those
identities to the baseline commit and hashes. Git remains the byte-level source
of the archived artifacts; the final active Dataset paths may be regenerated
for the quality-first release.

The pre-quality snapshot:

- is immutable;
- is not leaderboard data;
- is not mixed with final v0.7 results;
- does not count toward the final release hash;
- remains available for auditing why a Task was retained, rewritten, or
  retired.

The final v0.7 release gets new:

- Task replay identities when public Task truth changes;
- sanitized Prompt hashes;
- AgentTaskView hashes;
- Dataset and Slice hashes;
- RunManifest, Attempt, Cohort, and validation-report identities.

## 4. Lightweight Taxonomy

### 4.1 Design Rule

The taxonomy separates:

- what contract was violated;
- what conditions exposed the defect;
- where the behavior occurred;
- what failure was observed.

It does not force every diagnostic detail into a scored primary category.
Framework-specific root causes and components are optional diagnostic tags.

Formal Tasks must have valid required values. `unknown` and `other` are not
valid required values. Optional tags may be omitted when evidence is
insufficient.

### 4.2 Required Axis: `contract_family`

Each Task has exactly one primary `contract_family`:

| Value | Meaning |
|---|---|
| `result` | Mathematical value, numerical accuracy, or numerical stability |
| `tensor_metadata` | Shape, rank, dtype, device, layout, stride, or memory format |
| `mutation_state` | View, alias, in-place behavior, initialization, cache, or serialization |
| `gradient` | Autograd, first/higher-order gradient, or gradient-graph behavior |
| `api_behavior` | Signature, default, return structure, exception, or compatibility behavior |
| `efficiency_safety` | Performance, memory, crash, hang, leak, or termination behavior |

`contract_detail_tags` are optional controlled tags. Representative values
include:

- `value`;
- `numerical`;
- `shape`;
- `rank`;
- `dtype`;
- `device`;
- `layout`;
- `stride`;
- `alias`;
- `mutation`;
- `state`;
- `serialization`;
- `gradient`;
- `schema`;
- `exception`;
- `compatibility`;
- `performance`;
- `memory`;
- `liveness`.

Detail tags support analysis but do not create mandatory score buckets.

### 4.3 Optional Axis: `trigger_tags`

`trigger_tags` is an optional multi-label field:

- `empty_or_zero`;
- `scalar_or_low_rank`;
- `extreme_value_or_size`;
- `invalid_or_endpoint_parameter`;
- `noncontiguous_or_special_layout`;
- `mixed_dtype_or_precision_mode`;
- `dynamic_shape`;
- `mutation_or_alias`;
- `device_specific`.

Ordinary inputs require no synthetic `normal` tag.

### 4.4 Required Structured Axis: `execution_context`

Execution context is factual structured data, not a hierarchical category:

```json
{
  "devices": ["cpu", "cuda"],
  "modes": ["eager", "compile"],
  "phases": ["forward", "backward"],
  "distributed": false
}
```

Rules:

- `devices` is a non-empty subset of `cpu` and `cuda`;
- `modes` is a non-empty subset of `eager` and `compile`;
- `phases` is a non-empty subset of `forward` and `backward`;
- a Task counts as dual-device only after both paths have verified Runtime
  evidence;
- v0.7 does not admit Tasks whose required execution truth depends on hardware
  outside CPU and NVIDIA CUDA.

### 4.5 Required Axis: `failure_type`

Each Task has exactly one primary `failure_type`:

- `wrong_result`;
- `unexpected_error`;
- `missing_error`;
- `crash_or_hang`;
- `nondeterministic`;
- `performance_regression`.

Secondary manifestations may be recorded as optional detail tags, but only the
primary failure is used for release breakdowns.

### 4.6 Optional Diagnostic Tags

`root_cause_tags` are assigned only after Issue, reproducer, tests, and Gold
Patch support the diagnosis. Examples include:

- `overflow`;
- `incorrect_validation`;
- `wrong_dispatch`;
- `incorrect_cast`;
- `bad_gradient_formula`;
- `incorrect_lowering`.

`component_tags` are PyTorch-specific implementation locations, such as:

- `aten`;
- `autograd`;
- `dispatcher`;
- `dynamo`;
- `inductor`;
- `triton`;
- `cuda_kernel`;
- `distributed`.

Neither tag family is exposed to the Agent.

### 4.7 Example

```json
{
  "taxonomy_version": "v2",
  "contract_family": "result",
  "contract_detail_tags": ["numerical"],
  "trigger_tags": ["extreme_value_or_size", "device_specific"],
  "execution_context": {
    "devices": ["cuda"],
    "modes": ["eager"],
    "phases": ["forward"],
    "distributed": false
  },
  "failure_type": "wrong_result",
  "root_cause_tags": ["overflow"],
  "component_tags": ["aten", "cuda_kernel"]
}
```

### 4.8 Derived Slices

Slices are deterministic projections over the canonical 50-Task Dataset:

- Precision: `contract_family=result` with `numerical` detail;
- Boundary: one or more of `empty_or_zero`, `scalar_or_low_rank`,
  `extreme_value_or_size`, `invalid_or_endpoint_parameter`,
  `noncontiguous_or_special_layout`, or `dynamic_shape`;
- Device: CUDA execution context or `device` contract detail.

A Task may appear in more than one Slice. It is not duplicated as a Task Bundle
and contributes once to cumulative metrics.

Only a category with at least three verified Tasks receives a standalone
category score. Smaller categories are reported as case coverage without
representative-score claims.

## 5. Prompt Non-Leakage Contract

### 5.1 Scope

The existing AgentTaskView boundary remains. v0.7 adds a contract for the exact
public content supplied to the Agent and the Adapter's final rendered Prompt.

The formal Adapter must render the Prompt exclusively from the sanitized
AgentTaskView. It must not join TaskManifest, `issue.md`, Patch Scope, candidate
evidence, provenance, or Admission data at launch time.

### 5.2 Public Prompt Content

The public Prompt may contain:

- an opaque release Task ID;
- a neutral title;
- user-observable actual behavior;
- expected public behavior;
- a minimal black-box reproducer or public test entry point;
- inputs and outputs required to understand the behavior;
- necessary CPU/CUDA and eager/compile facts;
- naturally produced error text, logs, or stack traces when they are available
  to an ordinary reproducer;
- the user-facing API or feature name.

A natural stack trace is not automatically a location leak. Curator-added
diagnosis or a source path copied only to guide the Agent is a leak.

### 5.3 Forbidden Prompt Content

The public Prompt must not contain:

- PR, Commit, Patch Diff, Gold, or upstream fix provenance;
- internal Task IDs that encode PR numbers or descriptive slugs;
- exact Patch Scope or Task-specific writable paths;
- source file paths added as repair guidance;
- internal helper, function, or class names that are not naturally exposed by
  the public reproducer;
- root-cause conclusions;
- instructions such as "modify", "replace", "register", "reuse helper", "add a
  condition", or equivalent solution steps;
- Gold Patch size, changed-file count, or line count;
- Hidden Test names, selectors, assertions, or assets;
- taxonomy root-cause and component tags.

### 5.4 Public Identifier and Capability Policy

The Agent receives an opaque identifier such as:

```text
opbench-v07-t0037
```

The controller privately maps it to the canonical Task and provenance
identities.

`CapabilityPolicy.writable_paths` must be identical across v0.7 PyTorch Tasks
and broad enough not to reveal the target file. The intended public policy is
repository-wide source editing, represented by a repository-root scope rather
than Task-specific files.

Exact Patch Scope remains private in `FullTaskSpec` and is enforced after the
Agent freezes its final Patch. Agent-visible diff and final Patch capture must
include all repository changes so out-of-scope edits cannot disappear from the
submission.

`operator_name` in AgentTaskView names a public API or affected public feature.
Internal component names remain private diagnostic tags.

### 5.5 Sanitization and Review

The original Issue, PR, and provenance remain private evidence. The public
Prompt is an OpBench-authored statement derived from observed behavior; it need
not reproduce upstream text verbatim.

Prompt Admission runs:

1. deterministic provenance scan for PR/Commit/patch/test references;
2. overlap scan against Gold changed paths and private Patch Scope;
3. overlap scan against Gold-added symbols, helpers, distinctive literals, and
   solution phrases;
4. overlap scan against Hidden Test selectors and evaluation-only text;
5. blind human review of the Prompt and black-box contract;
6. full-context curator confirmation that sanitization did not change the
   intended behavior.

High-confidence leakage is a hard failure. Ambiguous overlap is deferred to
human review, not automatically accepted or rejected.

Prompt quality evidence records:

- sanitized statement hash;
- scan rule version;
- findings and disposition;
- blind-review decision;
- full-context semantic-equivalence decision;
- reviewer identities and timestamps.

Any Prompt change invalidates the previous AgentTaskView identity and requires
new Agent validation.

## 6. Complexity Admission

### 6.1 Hard Rejections

A Task is rejected regardless of Patch size when:

- the sanitized Prompt still makes the edit mechanical;
- the behavior has no meaningful user-observable or public-contract impact;
- the change is only spelling, formatting, cleanup, or constant movement without
  behavioral consequence;
- its trigger, diagnosis, and repair pattern substantially duplicate an
  existing formal Task;
- it fails any existing Source, Runtime, Baseline, Gold, F2P, P2P, Integrity, or
  provenance requirement.

### 6.2 Three-Dimension Rubric

Each dimension receives 0–2 points:

| Dimension | 0 | 1 | 2 |
|---|---|---|---|
| Localization | Prompt exposes the edit location | Search within one component | Trace across components, call paths, or execution paths |
| Diagnosis | Error directly implies the edit | Understand one contract or reproduced difference | Analyze interacting dtype, shape, Autograd, compiler, CUDA, state, or dispatch behavior |
| Repair and regression | Unique mechanical replacement | Choose repair location or preserve a neighboring path | Compare plausible fixes and protect backend, mode, or compatibility behavior |

Hard-rejection rules override the numeric total.

Decisions:

- 0–3: rejected;
- 4: boundary candidate; requires one sanitized-Prompt blind pilot and another
  human review;
- 5–6: eligible for the remaining Admission gates.

The blind pilot uses the same public capability boundary as formal validation,
but it is Admission evidence rather than a release Attempt. It cannot count
toward the 3-repeat or 1-repeat final validation budget, and its output cannot be
used to add solution hints back into the Prompt.

The final release contains:

- no `easy` Tasks;
- score-4 Tasks labeled `medium`;
- score-5/6 Tasks labeled `hard`.

### 6.3 Risk Signals

The following trigger extra review but never reject a Task alone:

- Gold Patch changes at most four source lines;
- Gold Patch changes one file;
- one Hidden F2P selector;
- all reference Agent attempts resolve the Task;
- a short wall-clock repair;
- a low number of tool calls or files read.

A one-line repair remains admissible when the sanitized Prompt requires real
localization, diagnosis, and semantic reasoning.

### 6.4 Complexity Evidence

Admission evidence records:

- the three scores and written evidence;
- hard-rejection check results;
- Patch file and source-line statistics;
- semantic-duplicate fingerprint and decision;
- whether blind pilot was required;
- blind-pilot identity and outcome when present;
- final difficulty label and reviewer decision.

Agent success alone is not Task truth. Behavioral evidence calibrates
difficulty; Baseline/Gold and tests determine validity.

## 7. Historical 25-Task Re-Admission

Every current Task follows the same process as a new candidate:

1. preserve its pre-quality identity in the audit descriptor;
2. author a sanitized public Prompt;
3. replace upstream/PR-derived public identifiers with an opaque ID;
4. remove Task-specific writable paths and internal operator hints from the
   Agent view;
5. run Prompt overlap scanning and blind review;
6. assign the lightweight taxonomy;
7. apply the complexity rubric;
8. rerun Baseline, Gold, F2P, P2P, Runtime, and Integrity;
9. run one independent Agent regression attempt with the new AgentTaskView;
10. retain, defer, or retire the Task with explicit evidence.

Let `k` be the number retained. Final expansion must produce `50-k` verified new
or replacement Tasks.

Prompt leakage in the old Task does not by itself retire the Task. The Task is
retired only when the sanitized version still fails quality, complexity,
runtime, semantic-duplicate, or standard Admission requirements.

## 8. Candidate Funnel and Final Dataset Composition

### 8.1 Candidate Volume

After historical re-admission establishes `k`, the captured candidate pool must
contain at least:

```text
3 × (50 - k)
```

real candidates.

Rejected and deferred candidates remain in the funnel report with reason codes.
If the verified count is below 50, search continues; Admission standards do not
change to fill the release.

Candidate search must include:

- CPU operator and framework issues;
- CUDA kernels and device-specific semantics;
- eager and compile paths;
- forward and backward behavior;
- Autograd, state, layout/alias, API, and safety/performance problems;
- issue and PR sources whose pre-fix revision and Gold truth can be frozen.

### 8.2 Contract-Family Soft Ranges

These ranges guide search and coverage reporting. They are not quotas that can
override Admission:

| Contract family | Target |
|---|---:|
| `result` | 10–12 |
| `tensor_metadata` | 9–11 |
| `mutation_state` | 7–9 |
| `gradient` | 7–9 |
| `api_behavior` | 6–8 |
| `efficiency_safety` | 4–6 |

### 8.3 Execution Coverage Gates

The final 50 Tasks must include:

- at least 30 CPU-backed Tasks;
- at least 15 CUDA-backed Tasks;
- at least 8 compile-path Tasks;
- at least 6 backward/Autograd Tasks.

A Task may count in more than one context only when every claimed context has
verified evidence.

### 8.4 Difficulty Gates

The final release contains:

- 0 easy Tasks;
- approximately 30–40 medium Tasks;
- approximately 10–20 hard Tasks.

The exact medium/hard split must sum to 50 and may vary with the verified pool.
It cannot be changed by lowering the complexity threshold or relabeling
rejected Tasks.

### 8.5 Derived Slice Targets

Because slices overlap, these counts do not sum to 50:

- Precision: target 10–14;
- Boundary: target 10–14;
- Device: target 15–20.

Coverage matrices must publish both achieved counts and explicit gaps.

## 9. Factory and Admission Data Flow

The quality-first path is:

```text
Raw Candidate
→ Private Provenance Capture
→ Source/Runtime Feasibility
→ Sanitized Prompt Draft
→ Prompt Overlap Scan
→ Blind Prompt Review
→ Taxonomy Review
→ Complexity Review
→ Task Bundle
→ Baseline / Gold / F2P / P2P
→ Integrity / Compatibility
→ Human Admission
→ Dataset Freeze
```

The existing Factory remains the backbone. v0.7 adds evidence and validation
for:

- Prompt quality;
- taxonomy v2;
- complexity;
- semantic duplication;
- pre-quality migration disposition.

Automation may discover risk and reject deterministic hard failures. Human
review owns:

- behavior-preserving Prompt rewriting;
- ambiguous answer overlap;
- root-cause and component tags;
- complexity scoring;
- duplicate semantics;
- final Admission.

## 10. Validation and Experiment Budget

### 10.1 Per-Task Validity

All final 50 Tasks must have:

- verified Source and Runtime;
- Baseline F2P failure;
- Baseline P2P pass;
- Gold F2P pass;
- Gold P2P pass;
- exact test-execution evidence;
- Prompt-quality evidence;
- complexity evidence;
- valid taxonomy v2;
- Artifact and replay integrity.

### 10.2 Agent Validation

Agent validation uses the frozen canonical Adapter, model configuration, Prompt
template, capability policy, budget, hardware class, and retry policy.

Repeat budget:

- each new or replacement Task: 3 independent attempts;
- each retained historical Task: 1 independent regression attempt.

Rules:

- Prompt modifications always create a new AgentTaskView hash;
- pre-quality attempts are not reused as final results;
- Agent resolution is reported but is not an Admission truth requirement;
- infrastructure-invalid attempts are not scored as Agent failures;
- final release reporting must contain zero accepted invalid Attempts;
- any infrastructure retry follows the frozen retry policy and is reported;
- changing Prompt, Task, Runtime, tests, scope, budget, or Adapter after an
  attempt invalidates comparability and requires a new Cohort.

### 10.3 Difficulty Calibration

Validation reports:

- resolved/no-patch/F2P/P2P outcomes;
- action, command, test, file-read, and wall-clock aggregates;
- medium/hard outcomes;
- task-level ceiling/floor concerns;
- failures attributable to Task, Agent, Evaluator, Runtime, or Infrastructure.

Tool-use behavior may support difficulty review. Hidden reasoning text is not
collected or scored in v0.7.

- historical re-admission report;
- expanded candidate-funnel report;
- cumulative 50-Task Dataset and Summary;
- derived Precision, Boundary, and Device Datasets and Summaries;
- taxonomy and coverage matrix;
- final Agent Validation Cohorts and report;
- revised Dataset Card;
- revised `docs/v0.7/design.md`;
- revised `docs/project_plan.md`;
- revised `docs/project_state.md`;

Derived Slice manifests reference the same canonical Task Bundles. They do not
copy or mutate task truth.

## 12. Failure Handling

| Condition | Decision |
|---|---|
| High-confidence Prompt answer leak | Reject Prompt version; rewrite and rescan |
| Prompt semantic drift from original behavior | Reject Prompt version |
| Blind/full-context reviewer disagreement | Defer for adjudication |
| Complexity score 0–3 | Reject Task |
| Complexity score 4 without pilot/re-review | Defer Task |
| Required taxonomy field cannot be assigned | Defer for taxonomy review |
| Missing CPU/CUDA evidence for a claimed context | Do not claim or count that context |
| Baseline/Gold/F2P/P2P/Integrity failure | Reject or defer Task |
| Semantic duplicate of an existing formal Task | Reject unless materially different behavior is documented |
| Fewer than 50 verified Tasks | Keep release open; do not lower standards |
| Infrastructure-invalid Agent attempt | Exclude from Agent outcome; handle under frozen retry policy |

## 13. Testing Strategy

### 13.1 Prompt Safety

Tests must prove:

- PR/Commit/Gold/Hidden identifiers are rejected;
- exact private paths and distinctive Gold symbols are detected;
- Task-specific `writable_paths` cannot enter a formal v0.7 AgentTaskView;
- public opaque IDs contain no provenance;
- internal component tags are absent from the Agent view;
- ordinary API names, black-box reproducers, and natural stack traces remain
  representable;
- all Adapter launch inputs are derived solely from AgentTaskView.

Positive and negative fixtures are required to control false positives.

### 13.2 Taxonomy and Complexity

Tests must prove:

- required enums and context structures validate;
- optional tags may be absent;
- required `unknown`/`other` values are rejected;
- derived Slice membership is deterministic;
- category-score reporting requires at least three Tasks;
- complexity totals, hard rejections, pilot requirements, and difficulty labels
  are deterministic;
- soft coverage ranges never bypass Admission.

### 13.3 Archive and Migration

Tests must prove:

- the audit descriptor binds commit `4f5addc` and exact pre-quality hashes;
- old and final cohorts cannot be combined;
- Prompt changes produce new AgentTaskView and comparability identities;
- retained and retired historical Tasks have explicit dispositions;
- the final Dataset contains exactly 50 unique verified Tasks.

### 13.4 Runtime and Release

Tests must cover:

- CPU and CUDA canaries;
- eager, compile, forward, and backward representative Tasks;
- Baseline and Gold execution;
- Hidden F2P/P2P execution truth;
- private Patch Scope enforcement after full Patch capture;
- deterministic Dataset/Slice/coverage rebuilds;
- full Schema, compile, JSON, link, safety, and repository test gates.

## 14. Revised v0.7 Delivery Phases

The completed P1–P5 history remains documented as the pre-quality baseline.
Quality-first expansion adds:

### P6 — Contract Rebaseline

- freeze this approved design;
- add pre-quality audit descriptor;
- define taxonomy v2, Prompt-quality, and complexity contracts;
- revise release scope and plan.

### P7 — Prompt and Historical Re-Admission

- implement Prompt overlap checks;
- remove Task-specific public path/provenance hints;
- sanitize and review all 25 historical Prompts;
- taxonomy-tag and complexity-score all 25;
- produce retain/defer/retire decisions.

### P8 — Candidate Expansion

- capture at least three times the post-audit deficit;
- build CPU/CUDA, eager/compile, and forward/backward candidates;
- run Compatibility, Admission, duplicate, Prompt, taxonomy, and complexity
  gates;
- reach 50 verified Tasks without lowering standards.

### P9 — Final Freeze and Validation

- freeze cumulative and derived Slice manifests;
- run Baseline/Gold/Integrity for all 50;
- run 3-repeat new/replacement and 1-repeat retained-historical Agent
  validation;
- publish coverage, difficulty, and failure analysis.

### P10 — Release Closure

- update Dataset Card, project plan/state, design, changelog, README, and docs
  index;
- reproduce all generated artifacts byte-for-byte;
- run final repository and release gates;
- mark v0.7 complete only after every criterion below passes.

## 15. Completion Criteria

v0.7 is complete only when:

1. `v0.7-pre-quality` is bound to commit `4f5addc`, old hashes, and old
   validation identities.
2. All 25 historical Tasks have documented re-admission dispositions.
3. The final cumulative Dataset contains exactly 50 unique verified Tasks.
4. Every final Task has a sanitized, reviewed, non-leaking Prompt.
5. No final AgentTaskView exposes provenance, exact target paths, private
   taxonomy, Gold, Hidden Test, or solution instructions.
6. Every final Task has valid lightweight taxonomy and complexity evidence.
7. No final Task is labeled `easy`.
8. CPU-backed count is at least 30 and CUDA-backed count is at least 15.
9. Compile-path count is at least 8 and backward/Autograd count is at least 6.
10. Precision, Boundary, and Device Slices are deterministically derived and
    publish achieved coverage and gaps.
11. All 50 Tasks pass Baseline, Gold, F2P, P2P, Runtime, and Integrity gates.
12. Every new/replacement Task has three valid Agent attempts.
13. Every retained historical Task has one valid Agent regression attempt.
14. Final validation accepts zero infrastructure-invalid Attempts.
15. Old and final Dataset/Prompt/Cohort identities are never mixed.
16. Generated artifacts rebuild byte-for-byte.
17. Full repository, Schema, compile, JSON, link, safety, and diff gates pass.
18. Public documentation describes the final 50-Task v0.7 truth and its
    limitations without leaderboard claims.
