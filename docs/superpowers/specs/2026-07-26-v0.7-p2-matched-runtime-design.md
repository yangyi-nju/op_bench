# OpBench v0.7 P2 Matched Runtime Design

Date: 2026-07-26

Status: Approved for autonomous implementation

## 1. Goal

P2 must give each previously deprecated Precision P4 task a new, evidence-backed
outcome:

- `pytorch__129154__exp_decomp_numerics`;
- `pytorch__144073__vector_norm_scalar_overflow`.

Each task is either restored to `verified` after a complete Baseline/Gold
Admission on a compatible runtime, or remains `deprecated` with new evidence
that identifies the failed compatibility strategy. Environment compatibility is
necessary evidence, but never substitutes for F2P/P2P execution.

## 2. Non-negotiable constraints

- The Base Commit, target source file, Hidden Test, Gold Patch, F2P selector and
  P2P selector remain unchanged.
- Compatibility must not be manufactured by editing Hidden Tests, monkeypatching
  missing APIs, skipping unrelated failures, or weakening assertions.
- A runtime is compatible only when its target module is loaded from the frozen
  Base Snapshot and all declared compatibility checks execute successfully.
- Baseline must reproduce the intended defect while preserving P2P. Gold must
  resolve F2P while continuing to preserve P2P.
- Official wheel, source-built wheel and full source build are attempted in that
  order. A later strategy is used only after the earlier strategy is unavailable
  or produces an unrelated compatibility failure.
- Runtime and build artifacts are content-addressed. Human-readable tags are
  aliases, not identity.
- Public evidence must not contain credentials, remote host addresses, absolute
  private paths, container handles or raw secrets.

## 3. Selected approach

P2 uses a small matched-runtime subsystem alongside the existing Factory and
Admission code.

1. A deterministic `CompatibilityEvidence` contract records each strategy
   attempt and its conclusion.
2. A probe runner executes an explicit list of compatibility checks and builds
   evidence from structured observations.
3. A CLI validates or records evidence without changing task status.
4. The existing Admission runner remains the sole authority for
   Baseline/Gold/F2P/P2P decisions.
5. A promotion command may update a task to `verified` only when compatible
   evidence and a verified Admission summary both bind to the same task,
   source, environment and replay hash.

The first wheel candidates are:

| Task | Base date | First official wheel probe |
| --- | --- | --- |
| `129154_exp_decomp_numerics` | 2024-06-20 | PyTorch `2.4.0+cu124`, CPython 3.11 |
| `144073_vector_norm_scalar_overflow` | 2025-04-04 | PyTorch `2.7.0+cpu`, CPython 3.11 |

These versions are the nearest retained stable official wheels after each Base
Commit. The target file is still overlaid from the Base Snapshot, so a wheel
that already contains the upstream fix cannot hide the baseline defect. The
probe rejects the wheel if its remaining Python/runtime APIs are not compatible
with that snapshot file and its frozen test path.

If a wheel probe fails for an unrelated API or ABI reason, an exact-commit build
is produced from a full snapshot. CPU builds disable CUDA and unrelated optional
components. CUDA builds target `sm_70`, matching the available V100 hardware,
and disable distributed components that the task does not exercise. Builds use
a commit-scoped ccache key.

## 4. Compatibility evidence contract

`matched_runtime_compatibility` schema version `v1` is a canonical JSON object
with a self-verifying SHA-256 content hash.

Top-level fields:

- `contract_type`, `schema_version`, `evidence_id`, `task_id`;
- `strategy`: `matched_wheel`, `source_built_wheel` or
  `full_source_build`;
- `status`: `compatible`, `incompatible` or `unavailable`;
- `source`, `runtime`, `build`, `checks`, `failure`, `created_at`;
- `content_hash`.

`source` records:

- exact 40-character Base Commit;
- snapshot content identity and identity kind;
- target module path and SHA-256;
- the expected target module runtime suffix.

`runtime` records:

- artifact kind, stable identifier, digest and digest kind;
- `torch.__version__`, Python implementation/ABI, platform;
- CUDA build/runtime versions, device name and compute capability when used;
- source-loading mode;
- observed target module path and SHA-256.

`build` records:

- exact normalized build flags;
- GPU architecture list;
- ccache key;
- source-built artifact digest, or `null` for an official wheel;
- toolchain summary.

`checks` is an ordered list. Every check has a stable name, command digest,
exit code, status and bounded public summary. Required checks are:

1. `source_identity`;
2. `runtime_identity`;
3. `target_module_provenance`;
4. `target_import`;
5. `selector_collection`;
6. `minimal_operation`.

`compatible` requires every check to pass, the observed target module hash to
equal the Base Snapshot target hash, and the runtime artifact digest to be
present. `incompatible` requires a stable failure code and at least one failed
check. `unavailable` records that an artifact could not be obtained or the
declared hardware/toolchain could not be reached.

The contract stores no full command output. Full logs remain run artifacts;
public evidence stores only bounded, redacted summaries and hashes.

## 5. Artifact and registry model

Compatibility evidence is stored at:

```text
tasks/pytorch/<task>/compatibility/evidence.json
```

Full run logs are stored under ignored run directories:

```text
runs/v0.7_matched_runtime/<task>/<strategy>/<timestamp>/
```

Wheel-based environments receive commit-specific registry IDs and Docker tags.
Exact-source fallback assets receive separate source registry IDs and paths, so
the existing sparse overlay snapshots are preserved.

An environment registry entry binds:

- task-compatible runtime tier;
- Docker image tag and observed immutable image ID;
- official/source-built wheel digest;
- Python/CUDA ABI;
- supported source-loading mode;
- remote resource requirements.

A source registry entry binds:

- upstream Base Commit;
- full snapshot path and deterministic source identity;
- submodule policy/status;
- compatible source-loading mode;
- related task.

## 6. Probe flow

The probe runner performs the following sequence in an isolated workspace:

1. verify the frozen source identity;
2. prepare the declared runtime;
3. apply the declared source-loading mode;
4. verify `torch`, Python ABI, CUDA and device observations;
5. hash the snapshot target file and the loaded runtime target file;
6. import the target module without compatibility exceptions;
7. collect exactly the declared F2P and P2P selectors without executing them;
8. execute a small non-F2P operation through the target API;
9. close the runtime and write canonical evidence.

Selector collection proves that the frozen test path can reach the named tests.
It is not allowed to execute the F2P assertion as part of compatibility
classification; that remains Admission's job.

Any infrastructure or cleanup failure is represented separately and cannot
become `compatible`.

## 7. Admission and promotion

After a compatible probe:

1. run the existing local preflight;
2. run Baseline Admission on a fresh workspace;
3. require F2P executed and failed for the intended signature;
4. require all P2P selectors executed and passed;
5. run Gold Admission in another fresh workspace;
6. require all F2P and P2P selectors executed and passed;
7. validate Gold Patch scope;
8. write stable Admission evidence;
9. bind the compatibility evidence hash into the task's admission metadata;
10. promote status to `verified`.

Promotion is fail-closed. It rejects:

- task/source/environment identity mismatches;
- missing or stale compatibility evidence;
- non-compatible evidence;
- Admission results other than `verified`;
- replay hash mismatch;
- missing test execution;
- out-of-scope Gold Patch.

If no strategy yields a compatible runtime, or a compatible runtime fails
Admission for a task-semantic reason, the task remains `deprecated`. Its notes
and compatibility evidence record the new stable reason without changing test
semantics.

## 8. Failure taxonomy

Stable compatibility failure codes:

- `artifact_not_found`;
- `artifact_digest_mismatch`;
- `source_identity_mismatch`;
- `python_abi_mismatch`;
- `cuda_runtime_mismatch`;
- `compute_capability_unsupported`;
- `target_module_not_from_snapshot`;
- `target_import_failed`;
- `selector_not_collected`;
- `minimal_operation_failed`;
- `build_failed`;
- `runtime_unavailable`;
- `cleanup_failed`.

Admission failures continue using the existing Admission taxonomy. Compatibility
and Admission failures are never collapsed into one field.

## 9. Testing

Unit tests cover:

- exact-field parsing and canonical round trips;
- self-hash verification and mutation detection;
- strategy/status invariants;
- source and runtime target hash equality;
- CUDA/build conditional requirements;
- public-data redaction and bounded summaries;
- deterministic probe command construction;
- failed/unavailable classification;
- promotion identity and replay-hash gates;
- schema parity with the Python contract;
- CLI validation and non-zero exit behavior.

Integration fixtures use small local Python packages and fake executors. They
must demonstrate that compatibility success cannot promote a task without
verified Admission and that verified Admission cannot promote a task with stale
compatibility evidence.

Live verification for each real task records:

- wheel availability/digest;
- probe outcome;
- fallback build evidence when needed;
- local preflight;
- Baseline result and executed counters;
- Gold result and executed counters;
- task status decision;
- artifact/schema/integrity validation.

## 10. Completion criteria

P2 is complete only when:

1. the contract, schema, probe and promotion tests pass;
2. each task has canonical compatibility evidence from a new v0.7 attempt;
3. each compatible task has full verified Admission evidence;
4. each incompatible task remains deprecated with a precise new reason;
5. registries contain only assets actually built and observed;
6. all changed schemas, registries and task manifests validate;
7. the full repository test suite and `git diff --check` pass;
8. `docs/v0.7/setup_matched_runtime.md`, design status and project state match
   the observed outcome.
