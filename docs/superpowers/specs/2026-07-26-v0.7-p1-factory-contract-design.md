# OpBench v0.7 P1 Factory Contract Design

Date: 2026-07-26

Status: Approved

## 1. Purpose

OpBench v0.7 begins with a contract-first Dataset Factory milestone. P1 freezes
the local, deterministic semantics needed to turn discovered PyTorch fixes into
auditable screening decisions and, later, verified dataset entries.

P1 deliberately does not:

- query live GitHub or the PyTorch mirror;
- run real Admission, Docker, SSH, CUDA, or source builds;
- create the formal `pytorch_v0.7` dataset;
- change the v0.6 Agent Runtime, evaluation, scoring, or trace model;
- add Agent-trajectory diagnosis or trace-based scoring.

The live candidate search, matched-runtime work, Boundary task admission,
validation cohort, and release remain v0.7 P2–P5 work. P1 provides the contracts
and deterministic fixture workflow those phases must use.

## 2. Design Principles

1. **Separate factory plane.** Dataset production state does not belong in the
   Agent Runtime or evaluator.
2. **Immutable evidence.** Re-screening or reviewing creates a new record; it
   does not rewrite an earlier decision.
3. **Stable identities.** Candidate identity is stable across repeated
   collection, while each captured record remains content-addressed.
4. **Derived decisions.** A screening disposition is derived from structured
   findings instead of trusting a free-form status string.
5. **Evidence-gated promotion.** A lifecycle state cannot advance without the
   evidence required for the target state.
6. **Historical compatibility.** v0.5 and v0.6 manifests, datasets, scripts, and
   results retain their original meaning.
7. **No quantity-driven weakening.** Factory contracts do not permit bypassing
   source, runtime, test, or taxonomy requirements to reach a task-count target.

## 3. Architecture

P1 adds a standalone package:

```text
src/op_bench/factory/
├── __init__.py
├── artifacts.py
├── contracts.py
├── lifecycle.py
├── screening.py
└── taxonomy.py
```

Responsibilities:

- `contracts.py`: strict immutable Candidate, Decision, Admission, and Freeze
  contracts with exact field validation and canonical serialization.
- `taxonomy.py`: Boundary B1–B5 definitions, failure contracts, keyword packs,
  and taxonomy validation.
- `screening.py`: deterministic hard filters and disposition derivation.
- `lifecycle.py`: allowed state transitions and evidence gates.
- `artifacts.py`: descriptor-safe immutable artifact writes, reads, hashes, and
  reference verification.

P1 adds thin CLIs:

```text
scripts/factory_screen_candidates.py
scripts/validate_factory_artifact.py
scripts/freeze_dataset.py
```

The existing `scripts/screen_candidates.py` remains the historical v0.5
precision screener. Existing builder, Admission, Dataset, and v0.6 Runtime
modules remain authoritative for their current responsibilities.

Data flow:

```text
local candidate fixture
        │
        ▼
CandidateRecord
        │  boundary keyword pack + hard filters
        ▼
DecisionRecord
   ┌────┼───────────┐
accepted rejected  deferred
   │
   ▼
Task bundle and Admission evidence references
   │
   ▼
FactoryAdmissionRecord
   │
   ▼
DatasetFreezeManifest
   │
   ▼
existing DatasetManifest and v0.6 Runtime
```

## 4. Contract Conventions

Every Factory contract uses:

```json
{
  "contract_type": "factory_*",
  "schema_version": "v1",
  "created_at": "2026-07-26T00:00:00Z",
  "content_hash": "sha256:..."
}
```

`content_hash` is the canonical SHA-256 of the payload excluding the
`content_hash` field itself. Canonical JSON uses the v0.6 implementation.

References use:

```json
{
  "artifact_type": "factory_candidate",
  "artifact_id": "candidate:v1:...",
  "content_hash": "sha256:...",
  "relative_path": "candidates/candidate-....json"
}
```

Factory public artifacts must not contain credentials, hidden-test contents,
Gold patch contents, host-private paths, or target handles. References may
identify private Admission assets by hash without embedding their contents.

## 5. CandidateRecord

`CandidateRecord` freezes the observed candidate and discovery context.

Required logical fields:

- stable `candidate_id`;
- framework, repository slug, PR number, and PR URL;
- base and merge commit identities;
- author date and merge date;
- title and bounded description;
- normalized changed-file records with path, additions, deletions, and test-file
  classification;
- total file and changed-line counts;
- discovery source (`fixture`, `git_log`, `github_pr_list`);
- keyword-pack identity and matched keyword IDs;
- proposed dimension and subclass;
- raw metadata artifact reference;
- collection timestamp.

`candidate_id` is derived only from repository, PR number, base commit, and
merge commit. Collection time and keyword matches do not change it. A repeated
capture with changed metadata has the same `candidate_id` but a different
`content_hash`.

P1 supports only local fixture input. The other discovery-source values are
reserved so P2 can add producers without changing the contract.

## 6. DecisionRecord

A `DecisionRecord` binds:

- Candidate identity and content hash;
- screening rule-set identity;
- target dimension/subclass;
- ordered structured findings;
- decision source (`automation` or `human_review`);
- optional prior Decision reference;
- derived disposition.

Each finding contains:

```json
{
  "code": "change.too_many_files",
  "severity": "reject",
  "rule_id": "v07-hard-filter-file-count",
  "message": "Changed-file count exceeds the automatic screening threshold.",
  "observed": 6,
  "expected": {"maximum": 3}
}
```

Allowed severities are `warning`, `defer`, and `reject`. Disposition is derived
as follows:

- any `reject` finding → `rejected`;
- otherwise any `defer` finding → `deferred`;
- otherwise → `accepted`.

The parser rejects records whose stored disposition does not match their
findings.

Reason-code namespaces:

- `metadata.*`
- `window.*`
- `change.*`
- `test.*`
- `source.*`
- `runtime.*`
- `taxonomy.*`
- `duplicate.*`
- `review.*`

Human review creates another immutable Decision. It may explicitly supersede
heuristic findings, but it cannot erase the prior record or override hard
source/runtime availability rules without new evidence.

## 7. Boundary Taxonomy and Keyword Packs

P1 freezes five Boundary subclasses:

- B1: empty and zero-size;
- B2: scalar and degenerate shape;
- B3: integer and size overflow;
- B4: parameter endpoints;
- B5: kernel launch and grid bounds.

Each keyword pack has:

- stable pack ID and version;
- dimension and subclass;
- positive phrase groups;
- negative/exclusion phrases;
- optional path hints;
- description.

Matching is deterministic and case-insensitive. Matching a keyword only
proposes a subclass; it does not prove root-cause classification. Accepted
automatic decisions therefore carry `review.root_cause_required` as a warning
until manual review occurs.

Task operator metadata gains optional explicit fields:

```json
{
  "problem_dimension": "boundary",
  "problem_subclass": "B3",
  "failure_contract": "crash-oob"
}
```

Historical tasks may omit them. When present:

- `boundary` requires B1–B5;
- `precision` requires P1–P5;
- `failure_contract` is one of `wrong-result`, `exception`, `crash-oob`, or
  `silent-acceptance`.

Tags remain auxiliary and no longer carry the authoritative failure contract.

## 8. Screening Rules

P1 implements the v0.7 automatic rules using fixture metadata:

1. reject revert/reland titles;
2. defer missing or unparseable author/merge dates;
3. reject candidates outside the stable author-date window unless an explicit
   environment-freeze exception is present;
4. reject pure refactor/cleanup or feature-only changes;
5. defer changes above the normal three-file or 200-line threshold for manual
   review rather than rejecting potentially valid generated-code exceptions;
6. reject changes below the minimum behavioral-change threshold when no
   executable test delta exists;
7. reject candidates without changed tests or an explicit external-test
   reference;
8. defer missing base/merge commit identities;
9. defer unsupported hardware/source requirements;
10. warn when root-cause classification still needs manual review.

The exact rule-set ID is frozen in the Decision and therefore participates in
comparability.

## 9. Factory Admission Lifecycle

Stored Admission states:

```text
discovered
  ├─ rejected
  ├─ deferred ──reassessment──> discovered
  └─ screened
        → bundled
        → preflight_passed
        → baseline_reproduced
        → gold_resolved
        → reviewed
        → verified
```

`rejected` and `deprecated` are terminal. A rejected candidate can only return
through a newly captured Candidate record. `deferred` may return to discovered
when the new record references the evidence that resolves the deferral.

Every promotion creates a new `FactoryAdmissionRecord` with:

- Candidate and accepted Decision references;
- optional Task identity;
- current state;
- previous Admission record hash;
- evidence references accumulated for completed stages;
- transition reason;
- actor kind;
- timestamp and content hash.

Required target-state evidence:

- `screened`: accepted Decision;
- `bundled`: Task bundle identity;
- `preflight_passed`: successful preflight evidence;
- `baseline_reproduced`: executed failing selector and failure signature;
- `gold_resolved`: matching source/runtime/selectors and resolved Gold result;
- `reviewed`: explicit human-review evidence;
- `verified`: all prior evidence plus integrity success.

The lifecycle implementation validates the full evidence set on every new
snapshot. It does not trust only the transition request.

## 10. Dataset Freeze

The Admission lifecycle ends at `verified`. `DatasetFreezeManifest` projects
selected verified records to frozen membership. This avoids a cyclic identity
between an Admission record and the Freeze that contains it.

A Freeze binds:

- dataset ID and version;
- base dataset identity;
- Factory protocol and rule-set identities;
- ordered selected entries;
- generated DatasetManifest identity;
- exclusion index identity;
- timestamp and content hash.

Each selected entry binds Candidate, Decision, Admission, Task, Admission
evidence, Source, Environment, and problem taxonomy identities.

Freeze validation requires:

- every selected Admission is verified;
- no duplicate Candidate or Task identity;
- all referenced artifacts match their recorded hashes;
- Boundary taxonomy is valid;
- selected entries use deterministic sorting;
- rebuilding produces byte-identical DatasetManifest output.

P1 exercises this behavior only with local synthetic fixtures. It does not
publish `datasets/pytorch_v0.7`.

## 11. Error Handling

Contract and artifact failures use stable machine-readable codes plus concise
messages. Categories include:

- `contract_invalid`
- `identity_mismatch`
- `artifact_missing`
- `artifact_unsafe`
- `transition_invalid`
- `evidence_incomplete`
- `decision_inconsistent`
- `freeze_not_rebuildable`

CLI behavior:

- exit 0: valid artifact or successful screening/freeze;
- exit 1: valid invocation but rejected validation or screening operation;
- exit 2: invalid CLI usage or malformed input.

Malformed input never produces a partially written output. Artifact writes use
temporary files, fsync where the existing platform requires durability, atomic
replacement for the new destination, and immutable-file checks thereafter.

## 12. Compatibility

- Existing v0.5 screener output and CLI remain unchanged.
- Existing Task fields remain valid; new taxonomy fields are optional for
  historical tasks.
- Existing Admission Evidence v1 remains authoritative for historical tasks.
- `FactoryAdmissionRecord` references rather than rewrites that evidence.
- Existing Dataset manifests remain valid.
- v0.6 comparability, evaluation, scoring, and historical run artifacts are not
  regenerated.

## 13. Test Strategy

P1 is test-driven and entirely local.

Contract tests cover:

- exact-field parsing and round trips;
- canonical identities;
- timestamp-independent Candidate identity;
- record-hash sensitivity;
- unknown enum and malformed hash rejection;
- public-artifact safety.

Screening tests cover every rule and Boundary keyword pack, finding ordering,
disposition derivation, repeated-run byte identity, and heuristic versus hard
failure behavior.

Lifecycle tests cover every valid edge, every forbidden edge, missing evidence,
identity mismatch, deferred reassessment, immutable history, and terminal
states.

Freeze tests cover deterministic ordering, duplicate rejection, missing or
tampered references, taxonomy validation, and byte-identical Dataset rebuild.

CLI tests use checked-in fixtures and verify exit codes, stdout/stderr,
canonical output, and atomic failure behavior.

Compatibility verification includes:

- existing focused builder/screener/admission/dataset tests;
- Task and Dataset validation;
- the complete repository test suite;
- `git diff --check`.

## 14. P1 Deliverables

- Factory package and public exports;
- four JSON Schemas;
- B1–B5 keyword-pack configuration or canonical code registry;
- local fixture candidates and expected decisions;
- three Factory CLIs;
- Task taxonomy Schema extension;
- focused and compatibility tests;
- `docs/v0.7/candidate_search.md` describing the frozen rule set and offline
  fixture results;
- project-state update marking P1 complete only after all gates pass.

## 15. P1 Acceptance Criteria

P1 is complete only when:

1. all four contract families round-trip and reject malformed records;
2. Candidate and record identity behavior is deterministic;
3. all B1–B5 packs have positive, negative, and ambiguous fixture coverage;
4. all screening findings use stable reason codes;
5. every lifecycle transition and evidence gate is tested;
6. a fixture Freeze deterministically rebuilds a DatasetManifest;
7. historical Task/Dataset/Admission artifacts still validate;
8. focused tests, full tests, schema checks, and diff checks pass;
9. no live network, Agent, Docker, SSH, CUDA, or remote Runtime was used;
10. no formal v0.7 Dataset was published prematurely.
