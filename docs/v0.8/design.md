# v0.8 设计与版本范围

范围修订于 2026-09-14，架构与文档整理于 2026-09-21，重复流程精简于 2026-09-22，按作者确认的第一阶段目标实施。本文替代此前以完全自主 Agent
和通用推理网关为核心的 v0.8 方案；历史实验保留其原始协议，不重新标成新框架结果。

## 第一阶段目标

在相同题目、工具、提示词、执行流程和预算下，比较不同模型解决算子问题的能力。
OpBench 提供固定模型循环及 MCP 工作区工具，由模型选择工具和参数；模型不能
自行换用其他 Agent 框架、连接外部检索服务或读取评测方资产。

| 版本 | 范围 |
| --- | --- |
| v0.8 | 修正工具、运行、构建、评分和恢复中的错误；模块解耦；精简为一个主指标 `resolved_rate` |
| v0.9 | 确定数据分类，每类至少 10 条独立任务；将选题、筛选、审查和准入流程放入项目，便于持续扩展 |
| v0.10 | 使用固定 MCP 框架完成多模型实验，记录可复核的结果，完成第一阶段 |
| 后续 | 固定模型比较不同 Agent 框架；行为分析、优化建议与完全自主 Agent |

v0.8 不以扩充数据、正式任务准入、统一模型比较或行为分析作为工程完成门槛。
“每类 10 条”按独立问题计数；环境变体、重复执行和同一缺陷的重复包装不凑题数。
分类体系留到 v0.9；当前可在任务 `metadata.category` 中记录描述，不写死在运行器中。

## 模块职责

代码按 `data/`、`runner/`、`runtime/`、`evaluation/`、`results/` 组织。
从哪一个文件开始读、模块怎样调用以及如何扩展，统一见[架构与源码导览](../architecture.md)。

```text
任务数据 → 固定运行框架 → 冻结补丁 → 独立评估 → 结果报告
                    ↓
               模型与工具轨迹
```

| 模块 | 职责 | 边界 |
| --- | --- | --- |
| 数据 | 加载题面、源码、环境、公开命令、评分配置与身份 | 不调用模型、不执行工具、不决定运行策略 |
| 运行 | 固定提示与模型循环、调用模型、派发 MCP 工具、控制预算、捕获补丁 | 不访问私有评分反馈、不判定最终修复 |
| 评估 | 独立准备候选、应用冻结补丁、构建和评分 | 不指导模型、不挑选更好的求解尝试 |
| 报告 | 从预先保存的计划与结果计算 `resolved_rate` | 不调整任务准入、不重跑模型、不改写原始结果 |

MCP 是固定工具实现的薄接口；不另建 Action Service、Bridge 或通用插件平台。
这些职责在一个 Python 程序内完成，`runtime` 只提供求解与评分共用的执行能力。
实验计划仅由 `run` 编排，不另设批量外部补丁实验入口。完整评分只保存在独立评分
目录；运行报告和手动重算共用一个函数，不维护评分缓存副本或报告版本链。
模型接入只负责把相同对话与工具调用协议适配到模型服务。常规 HTTP 模型接口和
本地 Codex 的 model-only 联调遵守同一循环；Codex 不能直接编辑任务工作区。
分析暂不实现，保留结构化轨迹即可，后续直接消费这些记录。

## 运行与信息边界

可信控制器持有题目包、模型凭据、模型客户端和固定循环。`controlled` 模式的工具
只操作分配的 Docker 工作区，工作区断网，不挂载控制器仓库、私有 grader、参考补丁或凭据。
构建与公开测试执行候选代码，因此同样在工作区隔离边界内运行。
显式 `development` 模式允许本机执行，供开发调试，不具备 Docker 的文件与网络隔离。

源码按选定基线导出，求解用 Git 只有干净的初始提交，没有上游未来历史和 remote。
固定依赖与可信基线在求解前准备。MCP 允许公开源码的合法修改与自测，权限不从
参考补丁涉及的文件推导。构建、公开测试和普通工具结果可以返回当前模型；
最终私有评分仅在求解结束、补丁冻结后执行，不返回同一次求解循环。

模型连接在控制器中完成，因此不再保留容器模型网关、relay 或任意 Agent 启动
命令。固定工具不能证明模型未记忆公开答案，也不能代替工作区隔离。
具体规则见[接入说明](agent_integration.md)和[信息边界](information_boundary.md)。

## 构建与评分

保留当前 Task schema 2、可信基线构建、独立候选副本和最终评分实现。每份补丁
均须进入实际加载的源码或构建产物。构建阶段没有私有 grader，最终评分不能仅
凭候选日志中的成功文本通过。空套件、跳过、观测缺失及评分错误分别处理。

`check-task` 保留基线、参考解、合理替代解和错误修复控制，用于开发评分器。
它不自动授予准入，也不要求开发任务先正式准入才能计算修复率。已支持的必需
环境变体共用一份补丁并按一道任务计分，本轮不建设新的多环境调度平台。
数值参考可与候选进程分离；需要共享框架进程的驱动如实说明防干扰限制。
任务接口与控制方法见[任务指南](task_format.md)。

## 指标、异常与恢复

唯一主指标为成功解决的任务数除以本轮预先选定的任务总数。每个模型每题默认
且本阶段只安排一次求解，所有模型使用同一集合。全部必需评分条件通过才算
`resolved`；超时终止与截止时补丁是否正确分别记录。服务响应正常时，模型未用
`finish` 结束、请求未知工具或提供非法参数也会终止求解、冻结补丁并独立评分，
按评分决定 resolved/unresolved，不因模型协议违规而让报告一直 incomplete。

缺失结果、环境或服务故障不从分母移除。存在未完成或不可确定项的报告标为
`incomplete`，比例仅表示当前进度。服务响应外壳损坏、工具执行器故障与模型给出
非法工具决策分别处理，前者属于基础设施错误。恢复不隐式重新调用已结束的模型；同补丁
的基础设施重评保留来源，不增加样本。新求解另建实验，不反复尝试后只留成功。
报告读取原记录并生成新报告，不在读取时修复或补写原始记录。详见[计分协议](statistical_protocol.md)。

## 当前取舍与维护

- 固定工具和循环有利于控制模型比较条件，但第一阶段结果不等于完全自主 Agent 能力。
- 断网与预置依赖限制临时下载；实验需提前提供解决题目所需的合理环境。
- 墙钟时间、步数与容器资源便于实施；同时间不等于同费用，用量未知时保留未知。
- 真实源码构建成本较高，基线可显式复用；仍须检查增量构建包含实际修改。
- 有限测试只能验证声明的范围，不能证明所有输入正确；任务、环境与评分器会持续维护。
